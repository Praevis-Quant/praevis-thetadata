## What the wheel establishes about authentication

The evidence below comes from `thetadata/client.py` in the supplied artifact, principally lines 64–182. Line numbers are retained in the inventory where applicable.

1. **Two protocols.** Constructor login is an HTTP POST to `https://nexus-api.thetadata.us/identity/terminal/auth_user`; data queries then use gRPC. Replacing the library with calls to the local REST server would be a different architecture.
2. **Request envelope.** The JSON contains `apiKey`, or `email` and `password`, plus `authEnv: {envType: ...}`. The `TD-TERMINAL-KEY` header value is bundled in the distributed source. It is a client identification/compatibility value, not the user's key; its longevity is undocumented.
3. **Actual credential order.** Reusing an existing client bypasses login. Otherwise an explicitly provided credentials file overrides API-key discovery, followed by API-key argument/environment, explicit email/password, and default credentials file. A constructor docstring implies API-key precedence more broadly than the implementation. Current Python docs explain the explicit-file exception.
4. **Discovery side effects.** `.env` loading occurs only when no explicit credentials file is used. MDDS environment selection happens before that load, so putting only `THETADATA_MDDS_TYPE` in `.env` may not affect the already selected environment. This port keeps environment discovery in the CLI and does not auto-load dotenv.
5. **Response assumptions.** The source indexes `sessionId`, `user.email`, and three subscription fields (`stockSubscription`, `optionsSubscription`, `indicesSubscription`). There is no typed identity response descriptor. Subscription values should not be treated as a locally authoritative entitlement policy; their shape/meaning can change.
6. **Opaque token.** `AuthToken` contains only `session_uuid`. `QueryInfo` carries the token, email hint, query parameters, and client/version metadata. No token is encoded as an HTTP Authorization header for gRPC in this artifact. No JWT structure, expiry claim, refresh token, or revocation request was found.
7. **Reuse is in-memory only.** `existing_authorized_client` copies token, email, subscriptions, and selected connection settings. It does not establish disk persistence or automatically renew credentials. Rust persistence is a project feature rather than a claim of Python parity.
8. **Environment and transport overrides.** The code selects PROD or STAGE MDDS hosts, defaults to port 443 and TLS, and exposes auth URL/MDDS host/port/insecure overrides. Inherited-client configuration has special rules; this port instead binds the session to its environment explicitly.
9. **Logging hazard.** Python logs the entire successful auth response at INFO (line 157), which includes `sessionId`, and rejection response text at ERROR. The Rust implementation deliberately avoids both. Enabling the vendor's suggested INFO logging without reviewing this behavior could expose tokens.
10. **Error scope.** Python raises `AuthenticationError` for non-success HTTP status, but malformed JSON/missing fields can produce generic exceptions. There is no auth-specific retry/backoff or explicit timeout argument in the call; HTTPX defaults still apply. Rust exposes typed errors and explicit deadlines, and does not invent retries.

## Response decoding and compatibility traps

These are artifact observations and future backlog candidates, not additional auth requirements:

- `ResponseData` carries bytes plus NONE/ZSTD compression, `original_size`, and an optional flat-file manifest. `DataTable` is a header list with rows of oneof values. A stream is a sequence of response batches, not a live subscription feed.
- Python accumulates every batch in lists before constructing a dataframe. Multi-GB exports therefore need an explicit streaming output design. Rust currently bounds each batch and yields it incrementally.
- Price values are int32 plus an index into scale factors. Scale zero maps to NaN in Python; Rust represents missing price as null and retains an exact mantissa/exponent. This is an intentional representation difference, not byte-for-byte dataframe parity.
- Numbers are int64; timestamps are unsigned epoch milliseconds with NEW_YORK/UTC enum values. New York is enum zero, so it cannot be treated as “timezone missing.” DST and timestamp bounds need explicit tests. Negative or out-of-range scale values must not index blindly into an array.
- The Python converter assumes row width matches headers, trusts compression metadata, and ignores flat-file manifests. A manifest-only message can yield an empty/default table rather than a useful download result. The flat-file byte framing beyond the descriptor still needs live/vendor evidence; Rust rejects manifest decoding rather than pretending it is supported.
- Generated Python wrappers often use truthiness guards. For example, `stock_history_trade_quote` (lines 627–675) omits an explicit `exclusive=False`; zero-valued rate/dividend/DTE inputs can also be omitted. Since omission may invoke a server default, later typed APIs must preserve `None` versus `Some(false/0)` and review documented defaults.
- Python gRPC NOT_FOUND is mapped to `NoDataFoundError`; other statuses are propagated. Do not map all empty results or permission errors to no-data. Terminal's proprietary HTTP statuses belong to a separate adapter.
- Current Rust generated query helpers expose wire structs. Python's optional defaults are not automatically applied, date/parameter validation is incomplete, and query metadata differs. This foundation is not full Python API parity.

## Questions for ThetaData

| Priority | Unverified contract | Why it matters |
| --- | --- | --- |
| Before unattended deployment | Session lifetime, idle expiry, and whether logins invalidate earlier sessions | Determines whether/how automatic recovery can be designed. |
| Before remote lifecycle commands | Supported introspection/refresh/revocation endpoints and error schema | Prevents inventing security-sensitive behavior. |
| Before multi-project live use | Account-wide identity/session limits, cross-process reuse, IP binding, concurrent login rules | Local persistence does not grant additional permitted connections. |
| Before relying on staging | Whether tokens and entitlements are environment-bound, and whether identity endpoint behavior differs | Confirms isolation assumptions and config. |
| Before publishing a supported SDK | Stability of the identity URL and terminal-identification header; official schema/versioning policy | The current contract is reverse-observed from the provided distribution. |
| Before data feature claims | Corporate-action availability, flat-file framing, direct-gRPC quotas, typed subscription payloads | Descriptors and REST documentation alone are insufficient. |

## Expansion order after auth

First close the live auth lifecycle questions and remaining auth test gaps. Next introduce a small validated data query and end-to-end protocol fixtures; then request defaults/presence and error taxonomy; then concurrency and bounded export; then flat files and real-time streaming as separately designed applications/adapters. Approve new L1/L2/L3 requirements and ADRs when those scopes are selected. No market-data feature is committed to a delivery date by this research.
